## 1. QUANDO USAR ESTE PERFIL

**Use quando:** site pessoal, portfólio, blog, landing page, documentação, institucional.
Com ou sem formulário, com ou sem vídeo, com ou sem área logada **rara**.

**Sinal de alerta — saia deste perfil se:**

- Começou a precisar de **RBAC**, **billing** ou **escrita concorrente**
- Virou **SaaS / dashboard autenticado / multi-tenant**
- Virou **e-commerce**
- Virou **tempo real / chat**
- Virou **IA / LLM / RAG** com vector DB

Em qualquer um desses casos, migre para o perfil adequado (ver §19).

## 3. REGRA DE UI — QUANDO USAR REACT

**Default: Astro puro, zero React.**

Só adicione React (e portanto shadcn/ui) quando **todos** forem verdadeiros:

1. Há estado local complexo (não apenas toggle de tema)
2. Há interação que Astro + `<script>` puro não resolve em < 30 linhas
3. O componente justifica o custo de hidratação (~40 KB de runtime)

**Casos que NÃO justificam React:**

- Header, Footer, Cards, Badges, Buttons estáticos
- Toggle de tema (10 linhas de JS puro)
- Menu mobile (HTML + `<details>` ou 20 linhas de JS)
- Accordion simples

**Casos que justificam React:**

- Combobox com busca assíncrona
- Editor rich-text
- Tabela com sort/filter/paginação client-side
- Formulário com validação cruzada complexa

**Regra:** se o site inteiro pode ter **zero React**, melhor. Cada ilha é dívida.

> Se ligar esta extensão, **deploy obrigatório em Cloudflare Pages** (GH Pages não roda server-side).

|--------|---------|---------|

> ⚠️ **Formulário NÃO usa D1.** Se um dia precisar persistir submissões, isso é Extensão 3 (Worker separado).

## 6. EXTENSÃO 3 — LOGIN + BD (ligue só se realmente precisar)

> **Regra:** se login é raro e DB é esporádico, isso **não vive no mesmo deploy do site**.
> Roda em **Worker separado** (repo separado ou monorepo).

| Camada | Escolha | Por quê |
|--------|---------|---------|
| Runtime | **Cloudflare Workers** (não Pages) | Pages não suporta Durable Objects, Cron, Queues |
| Framework | **Hono 4.13.x** | Ultra-leve, multi-runtime, middleware robusto |
| Auth | **Better Auth 1.6.x** + Drizzle Adapter | Sessão, OAuth, Passkeys, D1 nativo |
| Banco | **Cloudflare D1** (SQLite edge) | Read-heavy, escrita esporádica, zero compute-hour |
| ORM | **Drizzle 0.45.x** | Type-safe, edge-compatible, migrations |
| Validação | **Zod 4** | Schema tipado |
| Deploy | **Cloudflare Workers** | Separado do site Astro |

### 6.1 Quando migrar para Postgres (Neon/Supabase)

Migre se **qualquer** for verdadeiro:

- Escrita concorrente real (não esporádica)
- Transações ACID interativas
- Joins complexos / relatórios
- Multi-tenant
- Necessidade de full-text search sério

→ Nesse caso, você **saiu deste perfil**. Vá para um perfil SaaS.

## 7. GIT & CI/CD

| Camada | Escolha | Por quê |
|--------|---------|---------|
| Repositório | **GitHub** (sempre) | Padrão, Actions, Dependabot |
| CI | **GitHub Actions** | `astro check` + `build` + `linkinator` em todo PR |
| CD — GitHub Pages | `actions/deploy-pages` | Workflow oficial |
| CD — Cloudflare Pages | **Integração nativa Git** | CF builda direto do repo |
| Preview por PR | Cloudflare Pages (nativo) | GH Pages não tem preview nativo |
| Branch protection | `main` protegida, PR obrigatório | Evita quebrar deploy |
| Dependabot | Ativado | Atualiza deps sem lembrar |
| `.env` | No `.gitignore` desde o 1º commit | Use `.env.example` como doc |

### 7.1 Workflow mínimo de CI

```yaml
# .github/workflows/ci.yml
name: CI
on: [pull_request, push]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npm run astro check
      - run: npm run build
      - run: npx linkinator ./dist --recurse
```

Deploy fica com o provedor. Não duplique CD no Actions.

## 8. DEPLOY — GITHUB PAGES vs CLOUDFLARE PAGES

| Critério | GitHub Pages | Cloudflare Pages |
|----------|--------------|------------------|
| Banda | 100 GB/mês soft limit | Ilimitada |
| Build | GitHub Actions (você configura) | Nativo (integra no repo) |
| Functions/SSR | ❌ Não suporta | ✅ Pages Functions (10ms CPU Free) |
| Formulário server-side | ❌ Só client-side ou 3rd party | ✅ Astro Actions rodam aqui |
| Preview por PR | ⚠️ Manual | ✅ Automático |
| Deploy por push | ✅ Via Actions | ✅ Nativo |
| Redirects/headers | ⚠️ Limitado | ✅ `_redirects` / `_headers` |
| Custo | $0 | $0 |

### 8.1 Regra de decisão

- **GitHub Pages** → só quando o site é **100% estático**, sem formulário server-side, sem Functions, sem login, sem redirects server-side.
- **Cloudflare Pages** → quando tem **qualquer coisa além de estático**: formulário via Astro Actions, embed dinâmico, futura extensão de login, redirects server-side, headers customizados.

**Default recomendado:** **Cloudflare Pages.**
Migrar CF → GH depois é trivial (é só estático). O contrário é dor.

**Migração CF → GH:** trocar adapter do Astro para `output: 'static'` + apontar domínio. ~30 min.

### 8.2 Adapter correto para Cloudflare Pages

```js
// astro.config.mjs
import { defineConfig } from 'astro/config';
import cloudflare from '@astrojs/cloudflare';
import sitemap from '@astrojs/sitemap';
import tailwindcss from '@tailwindcss/vite';

export default defineConfig({
  site: 'https://<seu-dominio>',   // pré-requisito do sitemap
  output: 'static',                // site estático puro
  adapter: cloudflare(),           // ainda use: gera _headers/_redirects
  integrations: [sitemap()],
  vite: { plugins: [tailwindcss()] },
});
```

> **Não use `wrangler.toml`** se for Pages estático. `wrangler.toml` é para Workers.

## 13. SEO — PRÉ-REQUISITOS E ITENS OBRIGATÓRIOS

**Pré-requisito:** `site: 'https://<canonical>'` no `astro.config.mjs`.
Sem isso, o `@astrojs/sitemap` gera URLs relativas e o canonical quebra.

| Item | Obrigatório? | Onde |
|------|-------------|------|
| `site` no config | ✅ Sempre | `astro.config.mjs` |
| `sitemap.xml` | ✅ Sempre | via `@astrojs/sitemap` |
| `robots.txt` | ✅ Sempre | `public/robots.txt` |
| Meta `title`, `description`, `canonical` | ✅ Por página | layout |
| Open Graph + Twitter Cards | ✅ Por página | layout |
| JSON-LD `Organization` + `WebSite` | ✅ Sempre | layout raiz |
| JSON-LD `BreadcrumbList` | ⚠️ **Só se houver breadcrumbs visuais** | páginas internas |

> ⚠️ **Não adicione `BreadcrumbList` sem breadcrumbs visíveis.** Google penaliza dados estruturados que não correspondem ao conteúdo.

## 14. TEMA (DARK/LIGHT) — REGRAS

| Regra | Detalhe |
|-------|---------|
| Estratégia | Classe `.dark` no `<html>` (não media query) |
| Persistência | `localStorage['theme']` = `'light'` \| `'dark'` |
| Fallback | `prefers-color-scheme` quando não há preferência salva |
| AntiFlash | `<script is:inline>` **antes de qualquer CSS** no `<head>` |
| Scrollbar | `color-scheme: light dark` no `:root` (evita scrollbar branca no dark) |
| CSP-friendly | O script inline recebe hash automático no Astro 6 (sem `'unsafe-inline'`) |

### 14.1 Script AntiFlash canônico

```html
<script is:inline>
  (function() {
    try {
      const t = localStorage.getItem('theme');
      const dark = t === 'dark' || (!t && matchMedia('(prefers-color-scheme: dark)').matches);
      document.documentElement.classList.toggle('dark', dark);
    } catch (e) {}
  })();
</script>
```

**Ordem no `<head>`:** meta tags → AntiFlash → CSS → resto.
O `try/catch` protege contra Safari privado bloqueando `localStorage`.

## 15. TAILWIND V4 — TOKENS VIA `@theme`

Tailwind v4 **não usa mais `tailwind.config.js`**. Tokens vão em CSS:

```css
/* src/styles/global.css */
@import "tailwindcss";

@theme {
  --color-primary: #005F6B;
  --color-secondary: #94A69A;
  --font-sans: 'Inter', system-ui, sans-serif;
  --radius-lg: 0.5rem;
  --radius-xl: 0.75rem;
}

@custom-variant dark (&:where(.dark, .dark *));

:root { color-scheme: light dark; }
```

Depois use direto: `bg-primary`, `text-secondary`, `dark:bg-...`.

## 18. REGRAS DE DECISÃO TRANSVERSAIS

1. **Cloudflare Pages (Astro `output: 'static'`)** → site estático/SSG com Functions leves (10ms CPU Free).
2. **Cloudflare Workers** → Durable Objects, Cron, Queues, CPU > 10ms, ou auth/BD separado.
3. **D1** → read-heavy, edge-first, sem transações interativas concorrentes.
4. **Postgres** → ACID, concorrência de escrita, joins complexos, relatórios.
5. **Drizzle 0.45.x** é o stable; 1.0 é RC — não use em produção sem aceitar breaking changes.
6. **Astro 6** exige Content Layer API e Zod 4 — não é upgrade trivial do v5.
7. **Better Auth 1.6.x** é o stable; 1.5 introduziu D1 nativo.
8. **Vídeo:** sempre embed primeiro; só hospede se tiver motivo real (privacidade, DRM).
9. **Login:** só ligue quando tiver caso de uso concreto; "por precaução" é dívida técnica.
10. **Formulário:** sempre via Astro Actions + Resend; nunca monte endpoint próprio.
11. **GitHub Pages:** só para site 100% estático; qualquer coisa server-side → Cloudflare Pages.
12. **Secrets:** sempre no provedor (CF Dashboard / GitHub Secrets); nunca no repo.
13. **CI/CD:** CI no GitHub Actions, CD no provedor — não duplique.
14. **React:** só quando Astro + `<script>` puro não resolve em < 30 linhas (§3).
15. **Versões:** sempre fixar + datar. "Latest" é ambíguo.
