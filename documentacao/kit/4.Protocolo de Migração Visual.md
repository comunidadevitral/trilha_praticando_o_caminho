# PROTOCOLO DE MIGRAÇÃO VISUAL

> **Este documento é a fonte de verdade do que deve ser PRESERVADO em migração.**
> Em caso de conflito entre este protocolo e o `descoberta.md`, **este protocolo vence** —
> ele é a evidência do estado real do site original.
>
> Regras de operação estão em `AGENT.md`.
> Contexto do projeto está em `3.Formulário Mestre.md`.
> Como a IA pensa está em `1.Persona DEV.md`.
> Stack e versões estão em `2.stack-profiles.md` §0.

**Uso obrigatório** quando o projeto for classificado como **MIGRAÇÃO** ou **REDESIGN**
no `3.Formulário Mestre.md` (Bloco 2).

**Objetivo:** garantir que a migração de stack **preserve o visual e o conteúdo** do site
original, com paridade verificável e rastreável.

---

## COMO USAR ESTE PROTOCOLO

1. Preencher **antes** de qualquer implementação começar.
2. Coletar os artefatos nas pastas indicadas (`/baseline/`, `/tokens/`, `/inventory/`).
3. Anexar tudo ao repositório do projeto na pasta `/migration/` (não versionar binários pesados — usar Git LFS ou link externo).
4. Referenciar o protocolo no `descoberta.md` da fase de descoberta.
5. Rodar a validação (§D) **após** a implementação, antes de considerar a migração concluída.

### A.3 Ferramentas recomendadas

| Ferramenta | Uso |
|------------|-----|
| DevTools (Chrome/Firefox) → Device Toolbar | Captura em viewports específicos |
| `playwright screenshot` | Automação de captura em massa |

## SEÇÃO B — EXTRAÇÃO DE TOKENS

**Objetivo:** extrair os **design tokens reais** do site atual — não o que o
designer lembra, não o que está na documentação, mas o que **está no CSS** e
**é renderizado**.

**Artefato produzido:** `design-tokens-original.json` + `token-migration-map.md`.

> **Nota:** os comandos de extração factual (que rodam `grep` no CSS)
> estão em `documentacao/prompts/000-extração-original.md`.
> Esta seção descreve **o que fazer** com a saída — não os comandos.

---

### B.1 Como extrair (método recomendado)

**Passo 1 — Rodar a extração factual** conforme `prompts/000-extração-original.md`.

**Passo 2 — Abrir DevTools do Chrome no site atual.**

**Passo 3 — Aba "CSS Overview"** (Chrome 96+):

1. `F12` → menu `⋮` → **More tools** → **CSS Overview**
2. Clicar em **Capture overview**
3. Exportar cada aba:
   - **Colors** → exportar lista de cores com contagem de uso
   - **Font info** → famílias, tamanhos, pesos, line-heights
   - **Unused declarations** → o que está morto (bônus)
   - **Media queries** → breakpoints reais

**Passo 4 — Complementar manualmente:**

- Cores em gradientes (CSS Overview não captura)
- Espaçamentos (padding/margin/gap) via inspeção de componentes-chave
- Sombras (box-shadow) via inspeção
- Raios (border-radius) via inspeção

### C.3 Decisões sobre assets

Para cada asset, decidir:

| Decisão | Quando aplicar |
|---------|----------------|
| **Preservar 1:1** | Asset original em boa qualidade, formato aceitável |
| **Preservar com otimização** | Original em alta, mas formato antigo (ex: PNG → WebP) |
| **Redesenhar** | Original em baixa qualidade ou desatualizado |
| **Substituir** | Asset genérico (ex: ícone de outra lib) |
| **Remover** | Asset não mais usado |

Documentar a decisão por asset no CSV (coluna extra `decisao`).

## SEÇÃO D — ESTRATÉGIA DE VALIDAÇÃO DE PARIDADE

**Objetivo:** definir **como** a paridade será validada após a migração, e
**quais diferenças são aceitáveis**.

**Artefato produzido:** `parity-validation-plan.md`.

---

### D.1 Grau de paridade desejado

Marcar **uma**:

- [ ] **Pixel-perfect (imutável)** — cada pixel deve ser idêntico. Difícil, exige validação automatizada. Raramente viável por diferenças de rendering de fonte, antialiasing, sub-pixel.
- [ ] **Paridade visual fiel (recomendado)** — mesma hierarquia, cores, tipografia, espaçamento. Diferenças de 1–2px em rendering são aceitáveis. Validação humana + screenshot lado-a-lado.
- [ ] **Paridade com melhorias pontuais** — visual preservado, mas pequenos ajustes de a11y, performance ou UX são bem-vindos (desde que não alterem a identidade).
- [ ] **Paridade com melhorias estruturais** — UX/UI podem mudar; conteúdo é preservado. Já não é "migração fiel".

> **Regra:** "pixel-perfect" é um alvo aspiracional. Na prática, **"paridade visual fiel"** é o que se entrega em 95% dos casos.

---

### D.2 Ferramenta de validação

Marcar **uma** (ou combinar):

- [ ] **Manual** — screenshots lado-a-lado, revisão humana por página
- [ ] **Percy** (BrowserStack) — visual regression testing com baseline
- [ ] **Chromatic** — visual regression focado em Storybook
- [ ] **BackstopJS** — open source, CLI, aceita cenários
- [ ] **Playwright snapshot** — integrado ao runner, gratuito
- [ ] **Outra:** _______

**Recomendação por tamanho de projeto:**

| Tamanho | Ferramenta |
|---------|-----------|
| 1–5 páginas | Manual (screenshot lado-a-lado) |
| 5–20 páginas | Playwright snapshot ou BackstopJS |
| 20+ páginas | Percy ou Chromatic (baseline versionado) |

---

### D.3 Critério de aceite

Definir **o que conta como "paridade preservada"**:

```markdown
A paridade é considerada preservada quando:

- [ ] Nenhuma diferença visual perceptível em cores (ΔE < 2)
- [ ] Tipografia idêntica em família, tamanho, peso, line-height
- [ ] Espaçamento preservado (padding/margin/gap iguais)
- [ ] Hierarquia visual preservada (h1 > h2 > h3, destaque de CTAs)
- [ ] Responsividade preservada (breakpoints e comportamentos)
- [ ] Estados interativos preservados (hover, focus, active, disabled)
- [ ] Acessibilidade preservada ou melhorada (nunca piorada)
- [ ] Performance preservada ou melhorada (nunca piorada)
```

**Tolerância aceitável:**

- Diferenças de antialiasing de fonte: ✅ aceitável
- Diferenças de sub-pixel rendering: ✅ aceitável
- Diferenças de sombra por engine: 🟡 documentar
- Diferenças de cor > ΔE 2: ❌ corrigir
- Diferenças de espaçamento > 2px: ❌ corrigir
- Diferenças de tipografia: ❌ corrigir

---

### D.4 O que pode mudar (mesmo em paridade fiel)

Listar **explicitamente** o que é aceitável mudar sem quebrar a paridade:

```markdown
Mudanças aceitáveis (não quebram paridade):

- [ ] URLs limpas (`.html` → sem extensão) — com redirects 301
- [ ] Ordem de meta tags no `<head>`
- [ ] Minificação de HTML/CSS/JS
- [ ] Compressão de imagens (sem perda visual perceptível)
- [ ] Self-hosting de fontes (em vez de Google Fonts)
- [ ] Melhorias de acessibilidade (labels ARIA, contraste)
- [ ] Melhorias de performance (lazy loading, preload)
- [ ] Substituição de ícones por lib equivalente
- [ ] Adição de JSON-LD / meta tags de SEO

Mudanças NÃO aceitáveis:

- [ ] Alteração de hierarquia visual (títulos, CTAs)
- [ ] Alteração de paleta de cores
- [ ] Alteração de tipografia (família, tamanho, peso)
- [ ] Alteração de espaçamento entre elementos
- [ ] Remoção de elementos visuais (ainda que pequenos)
- [ ] Alteração de layout (posição de blocos)
```

---

### D.5 Fases de validação

Executar **em ordem**, com checkpoint por fase:

**Fase 1 — Validação por componente**

- Antes de montar páginas, validar cada componente isoladamente contra o baseline
- Screenshot do componente em ambos os sites
- Comparação lado-a-lado

**Fase 2 — Validação por página**

- Após montar cada página, validar contra baseline
- Todos os breakpoints
- Todos os estados

**Fase 3 — Validação cruzada**

- Navegar pelo site novo completo
- Comparar fluxo de navegação com o antigo
- Validar âncoras, links internos, links externos

**Fase 4 — Validação de responsividade**

- Testar em dispositivos reais ou simulados
- Viewports: 360, 390, 768, 1024, 1440, 1920
- Comparar com baseline correspondente

**Fase 5 — Validação final**

- Lighthouse (Performance, Acessibilidade, SEO, Best Practices)
- Axe DevTools
- Validação de HTML/CSS (W3C)
- Teste em navegadores: Chrome, Firefox, Safari, Edge

---

### D.6 Checklist final de migração

Antes de considerar a migração **concluída**:

**Visual:**

- [ ] Todas as páginas P0 com paridade validada
- [ ] Todas as páginas P1 com paridade validada
- [ ] Todos os estados (hover, focus, ativo, disabled) preservados
- [ ] Dark mode (se novo) sem regressão no light mode
- [ ] Todas as responsividades validadas

**Conteúdo:**

- [ ] Todo o conteúdo textual preservado (nada perdido)
- [ ] Todos os assets (imagens, SVGs, PDFs) presentes
- [ ] Nenhum link quebrado (validado com linkinator)
- [ ] Textos revisados quanto a encoding (UTF-8 correto)

**Técnico:**

- [ ] Lighthouse ≥ 95 em todas as categorias (ou meta definida em §7.9)
- [ ] Core Web Vitals dentro da meta (§7.9b)
- [ ] Acessibilidade WCAG 2.2 AA (ou nível definido em §5.9)
- [ ] SEO: sitemap, robots, JSON-LD, meta tags
- [ ] Redirects 301 configurados (se aplicável)

**Operacional:**

- [ ] Deploy no Cloudflare Pages funcionando
- [ ] Preview por PR funcionando
- [ ] Rollback testado
- [ ] Analytics (se aplicável) funcionando
- [ ] Banner de consentimento (se aplicável)

## REGRAS ESPECÍFICAS DO PROTOCOLO

> Regras universais de operação (extração factual, não inventar, proposta antes de construir)
> vivem no `AGENT.md`. Aqui ficam apenas as regras **específicas de migração visual**.

1. **Baseline é imutável.** Depois de capturado, não sobrescrever. Se o site mudar, nova pasta datada.
2. **Tokens extraídos vencem tokens "lembrados".** Se o designer diz "era #005F6B" mas o CSS Overview retorna `#005a66`, o CSS vence.
3. **Toda mudança visual durante a migração é documentada.** Se algo muda intencionalmente, entra em §D.4.
4. **Validação é por fase, não só no fim.** Erros de paridade descobertos cedo custam menos.
5. **Pixel-perfect é exceção.** Paridade fiel é o default.
6. **Screenshots ficam no repo.** Se não está versionado, não existe.
7. **Diff visual > tolerância bloqueia deploy.** Sem exceção.
